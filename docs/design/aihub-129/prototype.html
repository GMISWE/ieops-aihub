experience.pitfall

aihub Memory struct column-drift across 5 sites

aihub Memory struct (internal/domain/memory.go) has its column order replicated in FOUR places that MUST stay in lock-step: struct field order, the INSERT column list, the RETURNING + Scan, and scanMemory rows.Scan (whose SELECT list is the 5th place).

Adding a column requires editing all 5 sites with the SAME ordering or pgx Scan silently misaligns and corrupts neighboring fields - no compile error, no runtime panic, wrong values returned.

What / Why

The current /ui is a functional internal tool with no design system. Phase 1 delivers the shared design-system foundation plus the app shell, work item list, and work item detail.

Design decisions

D2 - aesthetic aligns to a Linear/Vercel developer-product feel (restrained, dark-friendly), tuned for team collaboration: identity and presence are first-class.

D3 - dual theme via CSS custom properties; theme is read from a cookie server-side+ Annotate to avoid FOUC, toggled with minimal JS.

Acceptance criteria

  • Documented dual-theme design tokens + component classes
  • Dark mode switchable, no FOUC, preference persists
  • No backend / API / DB changes; /v1 + /share byte-identical

Scope (Phase 1)

The shared design-system foundation: dual-theme greyscale tokens, type scale on Geist, a 4px spacing scale, one radius system, and component classes for buttons, badges, inputs, cards, list rows, person chips, activity feeds and comment threads.

The app shell: header navigation with active states, theme toggle, user chip; the login page moves to API-key-only sign-in.

Work item list with the six-segment queue summary and an All-projects / single-project switcher; work item detail with both dependency directions, a full artifact list and a readable activity feed.

Non-goals

No SPA framework, no npm build step, no backend or route changes. Memory pages and the artifact viewer ship as child work items blocked by this one; the annotation machinery from aihub#125 is preserved untouched in this phase.

No changes to recall or decay semantics; no new tables or columns; no modification of the /v1 API surface.

Rollout and verification

Each page lands behind the shared token layer first, then is restyled in place. go build and the render/server test suites must stay green on every step. Light and dark are screenshot-reviewed per page before merge.

The /v1 and /share artifact outputs are diffed byte-for-byte against the pre-change baseline in CI to enforce the invariant.

Risks

Dark-mode misses in inline styles and the login page's embedded CSS; chroma code-highlight contrast inside the app surface; the artifact viewer's annotation overlay must keep its alignment math when the document typography changes in the child work item.

References

aihub#124 and aihub#125 (annotation system), aihub#98 (artifact back-link), the design-comments record of the prototype iteration rounds, and the Design System page of this prototype as the living token source.

Review: Spec v2

methodology.review - agent reviewer (clean context) - target: mem_xfOviiEY v2 - 06-02

Verdict: PASS with findings - 1 must-fix, 1 suggestion, 1 nit. All addressed in v3.

Findings

must-fixDark-mode token coverage misses the login page

The cookie-based theme covers full page loads and HTMX swaps inherit correctly, but the login page carries its own embedded CSS and never receives the token layer. Add login to the shared tokens and extend the acceptance criteria accordingly. jump to spec section

shouldAcceptance criteria lack a measurable contrast check

"Readable in both themes" is not testable as written. Add an explicit WCAG AA pass (4.5:1 body, 3:1 large text) per page to the verification step.

nitVersion labels name the trigger inconsistently

"post-review" vs "initial" mixes trigger and ordinal. Name versions by what produced them: initial, post-review, post-annotation.

Checked

  • Scope matches the wi goal; phase split is implementable
  • Non-goals consistent with the aihub#125 /v1 + /share invariant
  • Child work item split (A memory pages, B artifact viewer) has clean boundaries
  • Risks enumerate the dark-mode and annotation-overlay hazards
  • No backend / API / DB changes implied anywhere

Outcome

Spec revised as v3 on 06-03 - all three findings resolved. This review is pinned to v2 and immutable.
