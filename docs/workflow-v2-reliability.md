# Workflow v2 — Batch4B reliability notes

This slice changes only local reliability helpers; it does not replace the workflow lifecycle or its database authority.

- `pf_diff` uses an explicit `refs/remotes/origin/HEAD` base for `vs_base=true`. It compares that ref directly with the index/worktree and appends ignored-rule-respecting untracked files as new-file patches. Staged, unstaged, committed-since-base and untracked changes are therefore visible together. An unset base is an error, not an implicit guess. The default comparison remains against `HEAD` (pending changes only).
- Cleanup checks that all supplied paths are siblings in one `pf.*` parent, refuses matching claimed credential state, dirty/untracked work and branches with commits absent from `origin/<task branch>`. Missing remote tracking information fails closed. Existing worktrees detach without `--force`; a missing directory can use force only to prune stale worktree metadata on retry. A failed detach retains the shared parent, even when other repos detached. **After a fully successful detach, the shared parent is removed only when it is actually empty** (Batch 4B review repair): the worktrees map is the attempt's own view, so the parent may still hold an omitted sibling repo worktree or a leftover scratch file — the engine reads the parent and refuses to hand a non-empty directory to the (recursive, caller-supplied) parent-removal callback, so an omitted sibling or scratch can never be destroyed by cleanup; the engine itself never removes anything recursively. A retained-because-non-empty parent is a safe outcome, not an error. This is intentionally stricter than the old unconditional deletion; warnings must be surfaced rather than interpreted as successful cleanup. Local tracking refs are the shipment check; a stale ref does not certify remote delivery after remote branch deletion.
- The chain sidecar is a display cache, not an attempt or step authority. A tool event must name its WI exactly (canonical ID, or a uniquely matched slug in a credential/sidecar); no most-recent-claim fallback is allowed, and duplicate/corrupt matches are ignored instead of selecting the first. **A response counts as success only when success is explicit** (Batch 4B review repair): an explicit normalized status, or the ACTUAL non-empty, error-free result the tool produced — never an empty object, an empty content array, or a bare `{isError:false}` a bridge synthesized after dropping the real result. Accordingly the pi bridge now forwards the tool_result event's real `content` + `isError`, and the opencode bridge forwards the `tool.execute.after` hook's actual result argument (the raw MCP CallToolResult for MCP tools, measured in opencode's own compiled source; MCP errors throw before that hook fires), so a successful lifecycle call advances the chain on those runtimes and a failed one cannot. Missing, ambiguous or error tool responses leave the cache untouched. Fused `next_step` completes the old step and activates its successor in one transition. Failed steps do not enter `done`; heartbeat does not complete a step; pause clears transient activity, while successful wrap/failure removes the sidecar.
