## Repo Routing (task → repo)

NL Routing above maps *intent → skill*. To decide *which repo/worktree* a task belongs to:

- **Which project / repo** — match the task against each repo's one-line `positioning` in
  the CLAUDE.md `## Workspace` block from Step 0; pick the repo whose role fits best.
- **Where to execute** — the claimed wi's worktree for that repo (`pf.<project>-<seq>/<repo>/`).
- **How to change** — this needs `main_modules` / `change_scenarios` / `tech_stack`. Get
  them in this order:
  1. **If `.polyforge/repo-map/<project>.md` exists → `Read` it.** `main_modules` locates
     the code, `change_scenarios` tells you whether the task is a known pattern,
     `tech_stack` sets tooling expectations (build/test commands). Read only the project
     you routed to, not every map.
  2. **Otherwise**, if the `## Workspace` block still shows two-space-indented
     `  - stack:` / `  - modules:` / `  - changes:` bullets nested under each repo (the
     repo-map file uses the same bullets *unindented*, so the indentation is what tells
     the two apart), this workspace has not re-run
     `polyforge init` since those moved out — the same four fields are already inline in
     your context. Use them from there; no read needed.
  3. **If neither is available**, say so — "repo map missing for `<project>`; run
     `polyforge init`" — and then use live tools (`codegraph_*`, `Grep`, a directory
     listing in the worktree) or ask the user. Do **not** infer a repo's internals from
     its one-line positioning.

For code *inside* the chosen repo, prefer live tools over the map: the map is a snapshot
regenerated by `polyforge init` and can lag the repo, while `codegraph_*` / `Grep` are
current.

When a task spans repos, route each part by the same map. If no repo clearly fits, ask the
user rather than guessing.
